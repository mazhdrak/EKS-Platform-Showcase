# Postmortem: Game day 001, injected 20% error rate

> **This is a planned exercise, not a real incident.** It validates that the alerting,
> dashboards and runbook work end to end. Replace the timeline with your own measured
> timestamps when you run it.

- **Type:** game day (fault injection)
- **Environment:** local (kind)
- **Status:** template for the exercise

## Hypothesis

If 20% of `/api/hello` requests fail, `DemoServiceErrorBudgetBurnFast` (14.4× burn,
threshold 7.2% errors) fires within about 5 minutes. The runbook leads the responder to
the change within 5 more minutes.

## Method

1. `make load` to establish steady traffic for 10 minutes.
2. Commit `FAULT_ERROR_RATE: "0.2"` in `apps/demo-service/deploy/base/deployment.yaml` and push.
3. Responder follows [the runbook](../runbooks/slo-burn.md) without prior knowledge of the change.
4. Mitigate by `git revert`.

## Timeline

| T+ | Event |
|---|---|
| 0:00 | Fault commit pushed |
| _fill_ | Argo CD synced; pods rolled |

| _fill_ | Error ratio back to 0; alert resolves |

## Things to look for

- **Detection delay** = Argo sync interval + rollout time + 5m window fill + `for: 2m`.
  Argo CD's default polling interval dominates. A GitHub webhook to Argo CD would cut it.
- **Budget cost.** At 20% errors the 30-day budget (0.5%) burns 40× faster than sustainable.
  Ten minutes at 20% errors costs about 1% of the monthly budget
  (2 error-minutes out of 216 allowed). The alert fires long before the damage is significant.
- **Does `kubectl rollout undo` work?** It should not stick, because self-heal reverts it.
  This confirms the runbook's warning.

## Action items (typical outcomes)

| Action | Type |
|---|---|
| Configure Argo CD webhook from GitHub to cut sync latency | detect / mitigate |
| Route `severity=page` from Alertmanager to an on-call tool | detect |
| Add a canary step (Argo Rollouts) so a bad release fails at 10% traffic | prevent |
